# DDD Narrative Output — Current Outline (2025-09-26 12:49)

## ゴール
- アジャイルで実装したコード資産と同じ階層構造を持つテキストファイル群（ナラティブツリー）を生成し、各ノードで概念定義と意思決定理由を提示する。
- 主対象は開発者自身の納得と追跡性。副次的に第三者が構造意図を辿れる。

## 成果物構成
- `narrative/` 以下にコードツリーをコピーしたディレクトリ構造を生成。
- 各ファイルノードには `.md` もしくは `.txt` で以下の枠組みを保持:
  - ヘッダ: 対応するコードファイルパス、生成日時、責任オーナー。
  - `Concept`: ファイル/モジュールが担う抽象的役割。
  - `Decisions`: 主要な設計判断（≤3件）と根拠へのリンク。
  - `Rationale`: 開発者が採用した理由、想定トレードオフ。
  - `Implications`: 他レイヤーへの影響や依存関係メモ。
- ディレクトリノードには `README.md` を設置し、配下の概要と整合指針を記述。

## 生成フロー（草案）
1. コードリリース確定時に対象ディレクトリをシリアライズし、ナラティブ用テンプレートにマッピング。
2. 各ファイルについて抽出可能なメタデータ（例: モジュール名、主要クラス/関数一覧）を自動記入。
3. 未記入の概念・意思決定欄は対話ログや `reports/` から引用し、足りない部分はレビュー要タスクとして `tasks/` に積む。
4. ナラティブツリー生成後、`reports/` にスナップショットをリンクし履歴管理。

## 決定事項
- D1: ナラティブツリーはコード階層と1:1で対応。
- D2: 独立した要件書は作らず、テキストファイル群が最終アウトプット。
- D3: 成果物は `narrative/` のファイル群として完結。

## 次の検討ポイント
- ノードごとの記述粒度（例: パラメータ/クラス/モジュール）をどう標準化するか。
- 自動抽出できるメタデータ項目と手動追記が必要な項目の境界。
- 生成トリガー（例: releaseタグ、特定Dump完了時）と履歴のバージョニング手法。

## 要質問
- 各ファイルに求める概念定義・意思決定理由の具体例を聞き取り、テンプレートを確定させる。
- テキスト形式のフォーマット（Markdown / YAML front-matter + Markdownなど）の希望。
